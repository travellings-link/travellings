# 开往网站收录申请规则

## 第一条 总则

### 1.1 规则目的

本规则用于明确网站申请加入「开往」（Travellings，以下简称「开往」）所应满足的条件、申请人应履行的义务，以及开往维护组（以下简称「维护组」）进行申请审核、日常巡查和收录管理时所适用的基本规则。

### 1.2 适用范围

任何希望将其网站提交至开往并参与友链接力的个人或组织，均应遵守本规则。提交申请即表示申请人已阅读并理解本规则，并愿意按照本规则及开往公布的相关规定参与收录。

### 1.3 基本原则

开往致力于促进开放、自由且互相连接的互联网。申请人应当认同开放网络理念，并愿意为此作出实际贡献，例如分享知识、经验或原创内容。

## 第二条 网站准入条件

申请收录的网站应当同时满足本条规定的基本条件。除本规则另有说明外，维护组将根据网站实际内容、访问情况及整体质量进行综合审核。

### 2.1 网站创办时间

2.1.1 网站应当已持续运营满两个月。

2.1.2 网站创办时间原则上以网站内第一篇文章的发布日期为计算依据。

### 2.2 内容数量与原创性

2.2.1 网站应当至少满足以下任一内容数量要求：

- 已发布不少于 20 篇文章；或
- 已发布不少于 10 篇原创文章。

::: info 关于 UGC 内容
据 开发维护组 内部裁定，UGC内容（既用户创作平台）无法加入开往 

[Issue#3832](https://github.com/travellings-link/travellings/issues/3832)
::: 

2.2.2 网站内容不得包含下列情形：

- 违反适用法律法规或公序良俗的内容，包括但不限于 [CSAM](https://www.cloudflare-cn.com/trust-hub/child-safety/)、涉政敏感、色情、暴力、血腥等内容；
- 严重影响访问体验的内容，包括但不限于侵入式广告、强制弹窗等；
- 大量重复、低质量或缺乏实质价值的内容，包括可通过搜索引擎检索到大量相同或高度相似内容的「内容农场」；
- 维护组认定的其他不适宜收录的内容。

2.2.3 对于多站点内容聚合，以及对源站未提供的数据进行统计、整理后形成的规范转载文章，不当然视为内容农场。

2.2.4 如网站在较短时间内发布的文章大部分属于使用人工智能生成且缺乏实质创作价值的低质量内容，维护组可以将其视同内容农场，并据此驳回申请。

### 2.3 网站更新情况

2.3.1 网站连续六个月及以上未更新的，维护组可以根据实际情况驳回其申请。

2.3.2 维护组建议申请人保持不定期或定期的内容更新，以维持网站的活跃度和可访问价值。

### 2.4 人工智能生成内容（AIGC）

2.4.1 开往不反对申请人使用人工智能工具辅助博客创作。

2.4.2 主要依靠人工智能生成的内容，必须明确标注为 AIGC。此类内容不计入本规则第 2.2 条所述的原创文章数量。

2.4.3 对于使用人工智能进行润色、资料查找等辅助工作的文章，开往建议申请人注明使用了 AIGC 技术辅助写作。

2.4.4 维护组在审核申请时，可以由维护组成员根据文章内容进行人工判断，以确定相关内容是否属于 AIGC。申请人可以依据开往运维规定提出复审要求。

### 2.5 特殊类型网站

2.5.1 引导页、个人主页及导航网站亦可以申请加入开往，但仍须接受维护组的综合审核。

2.5.2 对于单页面个人主页，维护组可能因其内容丰富程度不足而驳回申请。建议申请人通过多个页面对个人信息、作品或其他内容进行充分展示。

2.5.3 导航网站的收录资格由维护组根据其实际内容和质量具体判断。

2.5.4 如引导页、个人主页或导航网站链接了博客子站，则该博客子站仍应满足本规则中关于网站创办时间、内容数量、内容质量及更新情况的相关要求。

### 2.6 网站可访问性与安全

2.6.1 申请收录的网站必须能够正常访问。

2.6.2 网站可访问性以巡查机器人能否正常访问，以及维护组人工巡查时域名是否过期、网站是否仍由原有主体运营等情况作为判断依据。

2.6.3 网站必须启用 HTTPS。维护组建议申请人在技术条件允许的情况下启用 HTTP Strict Transport Security（HSTS）。

### 2.7 网站域名

2.7.1 开往强烈建议申请人使用自行付费注册并持有管理权的域名。

2.7.2 使用非付费域名的网站亦可以提交申请，但应遵守以下附加要求：

- 使用 `eu.org` 或 `github.io` 域名的新申请网站，将适用相对更严格的审核及巡查要求；
- 使用 Public Suffix List（PSL）所列域名的新申请网站，申请人必须先提交 eTLD 免责声明，并明确表示在知悉相关风险及限制后仍愿意继续申请；
- 对于未被列入 Public Suffix List 的非付费域名，开往原则上暂不接受其收录申请；网站质量极高的，维护组可以酌情处理。

2.7.3 Public Suffix List：<https://publicsuffix.org/list/public_suffix_list.dat>

### 2.8 `eu.org` 域名的特别要求

使用 `eu.org` 域名申请加入开往的网站，除应满足本规则其他适用条件外，还必须满足以下附加要求：

- 网站创办时间不少于六个月，计算方式以网站内第一篇文章的发布日期为准；
- 网站 UI 应当保持清晰、整洁，不得存在明显影响阅读体验的设计，例如可视度过低、可能造成视觉不适的配色或透明度设置；
- 网站至少应有 20 篇文章，其中不少于 10 篇为原创文章。

### 2.9 开往外链展示要求

2.9.1 申请人必须在其网站中放置开往的官方跳转链接：

<https://www.travellings.cn/go.html>

2.9.2 该链接应当放置在用户打开网站后能够直接看到的位置，例如网站顶栏、侧栏等。对于移动端页面，申请人应确保访客能够方便地找到该链接。

2.9.3 外链的文字、图标及展示方式应当符合以下建议：

- 英文导航文字建议使用 `Travelling`，而非 `Travellings`；
- 如使用图标或 Emoji，优先推荐火车、地铁相关图标，其次可以使用火箭、飞船相关图标；
- Font Awesome 6 推荐使用 [`fa-train-subway`](https://fontawesome.com/icons/train-subway?f=classic&s=solid)；Font Awesome 5 可使用 [`fa-subway`](https://fontawesome.com/v5/icons/subway?f=classic&s=solid)；
- Material Icons 用户可使用 `<mdui-icon-train></mdui-icon-train>`；
- Emoji 用户可使用 `🚇`；
- 不再推荐使用纸飞机图标，以避免与 Telegram 标识产生混淆。

2.9.4 如申请人希望进一步支持开往，或网站主题预置的开往外链在移动端不可见，可以在网站其他位置额外放置开往外链。

### 2.10 官方标识素材

申请人可以根据网站主题和实际展示需求，使用开往提供的官方标识素材：

| 素材类型     | 地址                                                     |
|--------------|----------------------------------------------------------|
| 动图 GIF     | <https://www.travellings.cn/assets/logo.gif>             |
| 深色 PNG     | <https://www.travellings.cn/assets/b.png>                |
| 浅色 PNG     | <https://www.travellings.cn/assets/w.png>                |
| 方形 PNG     | <https://www.travellings.cn/assets/travelling.png>       |
| 方形深色 PNG | <https://www.travellings.cn/assets/travelling-dark.png>  |
| 方形浅色 PNG | <https://www.travellings.cn/assets/travelling-light.png> |
| 矢量 SVG     | <https://www.travellings.cn/assets/logo.svg>             |

全部图片素材亦可查阅项目仓库中的 `assets` 文件夹。

如部分地区访问上述素材地址较慢，可以将地址中的 `https://www.travellings.cn/assets/` 替换为以下 CDN 地址前缀：

`https://cdn.jsdelivr.net/gh/travellings-link/travellings/assets/`

以下为外链展示参考代码：

```html

</a>
```

申请人可以根据网站主题调整所使用的图片素材及展示尺寸。有关展示位置的示例，请参阅开往官方文档中的相关示例。

## 第三条 申请与审核

### 3.1 申请渠道

3.1.1 申请人应前往开往 GitHub Issues 页面提交新的 Issue，并选择「申请收录」模板：

<https://github.com/travellings-link/travellings/issues>

3.1.2 申请人应按照 Issue 模板的要求提供必要信息，并确保所提交的信息真实、准确且有效。

### 3.2 同一域名下的多个网站

对于同一独立域名下提交的多个网站收录申请，如相关网站的内容相似或网站类型相同，维护组可以选择收录其中一个网站，或选择收录其引导页。

### 3.3 审核时间

3.3.1 维护组将在空闲时间内处理申请。申请审核时间可能因维护组成员的工作安排及申请数量而有所不同。

3.3.2 如申请提交超过一个月仍未得到审核，申请人可以在 Issue 中 @ 最近活跃的维护组成员，或通过开往已经公开的其他联系渠道进行询问。

### 3.4 申请驳回与后续处理

3.4.1 申请可能因不符合本规则、网站实际情况不满足收录条件或其他合理原因被维护组驳回。

3.4.2 对于需要申请人补充说明或跟进处理的申请，如申请人在 15 天内未作出回复，维护组可以关闭相应 Issue。

3.4.3 Issue 关闭后，如申请人仍希望加入开往，应重新提交申请。

## 第四条 收录后的维护与巡查

### 4.1 持续符合要求

网站获得收录并不意味着其永久满足收录条件。申请人应在收录后继续维护网站，并尽可能确保网站符合本规则所列的相关要求。

### 4.2 巡查与状态判断

维护组可以通过巡查机器人及人工巡查等方式检查已收录网站的可访问性、域名状态及其他与收录条件有关的情况。

### 4.3 规则适用

已收录网站亦应遵守开往公布的最新规则及相关运维规定。维护组可以依据实际情况对网站收录状态进行相应处理。

## 第五条 维护组权限与规则解释

### 5.1 规则制定与修改

开往维护组有权根据项目运行情况制定、调整和修改网站收录规则。

### 5.2 审核判断

对于本规则未明确列举的情形，维护组可以结合网站实际情况、开放网络理念及项目维护需要进行综合判断。

### 5.3 规则解释

开往维护组保留对本规则的解释权。规则发生修改时，以最新公布的版本为准；规则更新后，原则上不另行逐一通知申请人或已收录网站的站长。

## 第六条 参与项目与页面贡献

### 6.1 参与方式

除提交网站收录申请外，任何有意愿为开往项目作出贡献的参与者，亦可以向项目提交跳转页样式或其他相关改进。

### 6.2 跳转页样式提交要求

如参与者希望在项目的 `public` 文件夹中提交新的跳转页样式，应满足以下要求：

1. 页面涉及的所有图片均必须使用 SVG 格式；
2. 页面必须为单页 HTML。CSS 可以直接写入 HTML 文件头部；JavaScript 库应使用外部公共 CDN；
3. 页面底部必须包含开往备案号，以及指向[开往偏好设置](https://www.travellings.cn/preference)的链接；
4. 页面应嵌入 `https://www.travellings.cn/assets/js/go.js`，以实现跳转逻辑并自动使用用户的偏好设置；
5. 页面设计应当具有良好的视觉效果或创意；
6. 参与者应同步修改[其他页面一览](/docs/pages)，添加所提交页面的描述及截图；
7. 参与者应同步修改开往偏好设置，修改位置为 `.vitepress/theme/components/Preferences.vue`，并将自定义页面加入设置菜单；
8. 完成上述工作后，应向项目提交 Pull Request，并 @ 最近活跃的维护组成员。

### 6.3 参考与注意事项

对于不熟悉页面开发的参与者，可以在现有跳转页的基础上进行修改。

如果参与者以默认的 `go.html` 为基础制作自定义跳转页，必须先删除 `<head>` 中用于自动跳转至用户自定义页面的以下代码：

```html
<script>
    const customPage = localStorage.getItem("t_preference_page");
    if (customPage) {
        location.href = "./" + customPage;
    }
</script>
```

上述代码用于使默认跳转页自动跳转至用户设置的自定义页面。如果自定义页面本身仍包含该代码，可能导致页面循环跳转。

## 第七条 其他

### 7.1 规则效力

本规则自公布之日起适用。维护组后续公布的修订版本适用时，以最新版本为准。

### 7.2 联系与反馈

有关申请、审核或规则适用的问题，申请人可以通过开往 GitHub Issues 或维护组已经公开的联系渠道反馈。
